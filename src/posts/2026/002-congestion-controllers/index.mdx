Rate limits and concurrency limits are simple, useful tools. They also hide an awkward question: how did we decide what the limit should be?

This post will work towards an answer by making the system interactive. Start with the experiment below. The clock runs continuously, but the interesting event should happen because you changed something.

## What this first experiment shows

The service has four workers, each with its own small FIFO queue with room for four requests. Each worker usually takes about a second, but its performance fluctuates a little from one moment to the next. The load balancer randomly routes jobs to workers, and the shared network path adds latency that the client cannot see directly. Each moving dot is a job: it leaves a specific client, crosses the network, waits in that worker's queue, and is then picked up by the worker.

With a rate limit, every client keeps sending at the same rate even when the service slows down. Adding clients multiplies the offered rate; once one worker's finite queue fills, new jobs routed there are rejected instead of waiting forever.

With a concurrency limit, the client keeps a fixed number of requests in flight. As observed latency rises, the client naturally sends less work. That is already a useful improvement—but it still needs a way to choose and adjust the concurrency limit.

The three adaptive controllers make that choice continuously. AIMD increases its window cautiously and cuts it when a request is rejected. Vegas watches for extra delay before the queue fills. Gradient2 compares short- and long-term latency, looking for a trend rather than reacting to one noisy sample.

The next iterations will add the metrics that help us understand the system—USE for resource health and RED for request health—and make the controller feedback visible in more detail.
