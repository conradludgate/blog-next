Rate limits and concurrency limits are simple, useful tools. They also hide an awkward question: how did we decide what the limit should be?

This post will work towards an answer by making the system interactive. Start with the experiment below. The clock runs continuously, but the interesting event should happen because you changed something.

## What this first experiment shows

The service has a small FIFO queue with room for twelve requests in front of four workers. Each worker usually takes 250ms, but its performance fluctuates a little from one moment to the next. The shared network and load-balancer path adds latency that the client cannot see directly. Each moving dot is a job: it leaves a specific client, crosses the network, waits in the queue, and is then picked up by a specific worker.

With a rate limit, every client keeps sending at the same rate even when the service slows down. Adding clients multiplies the offered rate; once the finite queue fills, new jobs are rejected instead of waiting forever.

With a concurrency limit, the client keeps a fixed number of requests in flight. As observed latency rises, the client naturally sends less work. That is already a useful improvement—but it still needs a way to choose and adjust the concurrency limit.

The next iterations will add the metrics that help us understand the system—USE for resource health and RED for request health—then use the same surface to explore client-side congestion controllers such as Vegas and Gradient2.
